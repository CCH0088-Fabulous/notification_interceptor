# ADR 0008：取消确认改为回调驱动，落盘移出关键路径

- 状态：已采纳
- 日期：2026-10-18

## 背景

最初的取消流程是同步的：

```
cancelNotification(key) → Thread.sleep(250) → 查 activeNotifications → 落盘
```

这样写是为了让 `cancelStatus` 立刻给出三态结果（`success` / `rejected` / `failed`），
便于验收。但它把「确认取消生效」和「取消本身」绑在了同一条关键路径上。

插桩实测（单条投递，24 条样本）暴露了代价：

| 路径 | 均值 | 说明 |
|---|---|---|
| 拦截（取消 + 校验） | 466.7 ms | |
| 保留（只判定） | 212.9 ms | 不取消 |

**差值 253.8 ms**，与代码里写死的 `DEFAULT_DELAY_MS = 250L` 吻合到 4 ms。
两条路径跑的是同一套代码、同一个引擎、同一个落盘，唯一差别就是"取消 + 校验"。
拆解后的构成：

| 构成 | 实测 | 占比 | 性质 |
|---|---|---|---|
| 系统分发（post → 回调） | ~210 ms | 45% | 平台边界，不可消除 |
| 校验的固定等待 | 250 ms | 54% | 自设常量 |
| 判定 + `cancelNotification` IPC | ~7 ms | 1% | 基本不可压缩 |

批量场景更严重：40 条/轮时 p95 达 9663 ms。单线程 worker 每条要做
`250 ms（等待）+ ~115 ms（写盘）+ ~10 ms（判定）`，40 条累积成 4–5 s 排队。

## 决策

1. **取消确认由 `onNotificationRemoved` 回调驱动**
   - `cancelNotification` 之后只登记 `key → 待确认记录`，立刻返回；
   - 系统移除通知时回调，直接判定 `success`；
   - 1.5 s 内无回调（被系统静默拒绝）时，做**一次**非阻塞 `activeNotifications` 复查，
     通知仍在 → `rejected`，已不在 → `success`。
2. **历史落盘移出处理线程**：单独 IO 线程，顺序由单线程执行器保证。
3. **新增中间态 `CancelStatus.PENDING`**：只在内存里存在。历史在确认后才写，
   因此 `history.jsonl` 里永远只有终态（实测 1000 行，`pending` 0 条）。

## 为什么不用"立即查一次 activeNotifications"

`cancelNotification` 是异步的：返回成功只代表请求被接受，移除可能滞后数百毫秒。
删掉等待后立即查询，会把"尚未传播"误判成 `rejected` —— 这正是最初把
`attempts` 改成 3 次轮询的原因。回调消除了这个竞态：系统告诉我们"已经移除了"。

## 结果

同一台模拟器、同一套规则：

| 指标 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| 单条 · 拦截 | 466.7 ms | **208.6 ms** | **-55%** |
| 单条 · 保留 | 212.9 ms | 208.8 ms | — |
| 批量（40 条/轮）均值 | 5219 ms | **319.8 ms** | **-94%** |
| 批量 p95 | 9663 ms | **435 ms** | **-95%** |
| 批量 p99 | 10552 ms | **481 ms** | **-95%** |
| 取消成功率 | 100% | 100% (452/452) | 不变 |
| 判定质量 | 漏 0/451 · 误 0/452 | 漏 0/452 · 误 0/451 | 不变 |

拦截路径（208.6 ms）与保留路径（208.8 ms）现在**在统计上不可区分** ——
说明「取消通知」本身几乎不花时间，剩下的 208 ms 全是系统分发。

`observe-ongoing` / `observe-progress` 仍在 ~1.5 s 后正确记为 `rejected`，
`observe-noclear` 仍为 `success`，行为没有退化。全量 e2e 复测：
PASS 11 / FAIL 0 / OBSERVED 8，与优化前一致。

## 代价

- **`cancelStatus` 不再立即可读**：实时流里看不到取消结果，要等历史落库。
  影响很小：`NotificationRecord` 本来就不带 `cancelStatus`，UI 只在历史页展示。
- **进程被杀时队列里的历史条目会丢**。历史是审计用的旁路数据，
  不影响"取消是否生效"这一主链路，因此接受。
- **`rejected` 的检出延迟变成约 1.5 s**（超时时间）。验收脚本的等待窗口是 10 s，不受影响。
- 多一个线程（`notif-history-io`）和一个定时器线程（`notif-cancel-timeout`）。
