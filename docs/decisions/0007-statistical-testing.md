# ADR 0007：用统计检验替代"跑一遍没报错"

- 状态：已采纳
- 日期：2026-10-17

## 背景

`tool/metrics.ps1` 已经能算混淆矩阵和 P/R/F1，但它回答不了三个必然会被问到的问题：

1. **会不会漏掉？**（该拦的没拦）
2. **会不会误拦截？**（不该拦的拦了）
3. **平均拦截时间是多少？**

更难的是第三层的诚实性：现有 e2e 单次运行只有几十条样本，0 个错误时报告
"准确率 100%"。这在统计上没有意义——22 条样本 0 错误，真实错误率的上界仍
在 12% 量级。用这种数字宣称"不会漏"是误导。

## 决策

### 1. 把"采样"和"断言"分开

新增 `tool/e2e.ps1 -Bulk <N>`：只发通知、只收集记录、不做断言。

- 每轮 40 条生成器通知（`--el seed <轮次>`，可复现）；
- 每轮结束等历史条目到齐，按 `channelId + 关键词` 独立推导 ground truth，
  写进 JSON 的 `expected` 字段；
- 规则侧用 `assets/presets/generator_triage.json`，与 UI 一键导入的预设同一份；
- 不满足数量的部分（系统对单应用有通知速率限制）按实收数量统计，
  并在 `detail` 里同时记 `samples` 与 `requested`，用来算采集率。

### 2. 检验由独立脚本做（`tool/stats.ps1`）

不在 e2e 里算，理由同 ADR 0005：断言与度量解耦，度量可复算、可回归。

三个问题各自的统计口径：

| 问题 | 点估计 | 区间 | 假设检验 |
|---|---|---|---|
| 会不会漏掉 | 漏拦率 = 漏拦 / 应拦 | Wilson score 95% | 单侧二项，H0: p ≥ p0 |
| 会不会误拦 | 误拦率 = 误拦 / 应留 | Wilson score 95% | 单侧二项，H0: p ≥ p0 |
| 平均拦截时间 | `decisionTime - postTime` 均值 | bootstrap 2000 次 + 正态近似 | — |

**为什么用 Wilson 而不是正态近似**：极端比例（0% / 100%）下正态近似的区间会
退化成一个点或越过 [0,1]，Wilson 在小样本和极端比例下都稳定。

**为什么还要 rule of three**：0 错误时区间下界恒为 0，上界才是唯一有信息量的
数字。`3/n` 是最容易记住的形态，与 Wilson 交叉验证可以互相校验实现没写错。

**为什么单侧而不是双侧**：我们要证的是"错误率低于某个阈值"，不是"错误率不等于
某个阈值"。单侧检验在同样样本量下功效更高。

### 3. 时延必须分档

第一版把批量投递和单条投递混在一起算，得到 mean 5500 ms —— 这不是判定开销，
而是 40 条通知在单线程队列里**排队**的时间。分档后：

- 单条投递：约 300–600 ms，这才是对外承诺的口径；
- 并发批（±2000 ms 内多条）：约 4–5 s，反映吞吐上限，看 p95 而非均值。

分档规则写在脚本里：同一 scenario 内 `postTime` 相距 ≤ 2000 ms 视为同一批。
不用固定场景名单，避免新增场景时忘记归类。

### 4. OBSERVED 场景不进判定质量

`observe-ongoing` / `observe-progress` 这类场景记录的是"系统拒绝取消 ongoing 通知"
这一 Android 事实，不是规则判定错误。把它们算进"应拦未拦"会凭空制造 2 个漏拦样本。
与 `metrics.ps1` 口径一致：剔除，但在报告里单独披露条数。

### 5. 门禁用点估计，结论用区间

`-Gate` 只看点估计（漏拦率 / 误拦率 ≤ `-MaxErrorRate`、重复率 = 0），因为门禁要
稳定可复现；"能不能宣称 < 1%"这类结论由 p 值和 sample size 决定，写在报告里给人看，
不进门禁——否则样本量不足时门禁会随机失败。

## 结果

首次执行（903 条：应拦 451 / 应留 452，采集率 100%），详见
[docs/verification/stats.md](../verification/stats.md)：

| 问题 | 答案 | 依据 |
|---|---|---|
| 会不会漏掉 | 0/451，95% 上界 0.845% | Wilson + 单侧二项 p=0.0108 → 可宣称 <1% |
| 会不会误拦截 | 0/452，95% 上界 0.843% | Wilson + 单侧二项 p=0.0106 → 可宣称 <1% |
| 平均拦截时间 | 单条 310.5 ms，95% CI [280.2, 340.8]，p95 470 ms | bootstrap 2000 次 ≈ 正态近似 |
| 批量时延 | 均值 5219 ms、p95 9663 ms（n=838） | 单线程队列排队，非判定开销 |

由此得到一个可复用的判据：**样本量决定结论强度**。0 错误时可宣称的上界 ≈ 3/n，
n=300 → <1%，n=600 → <0.5%。"证明不会漏"因此是一个能算出需要多少样本的问题，
而不是一句定性描述。本轮 451/452 条已够宣称 <1%，但不够宣称 <0.5%。

## 代价

- 一次 bulk 采样约 10–20 分钟（40 条/轮 × 10 轮，受系统限流影响）；
- 采集率不会到 100%（系统会丢一部分），报告里必须同时给出实收与请求数；
- ground truth 与预设规则同源，只能发现"规则引擎实现错了"，发现不了
  "规则本身写错了"——后者仍需人工复核预设文件。
