# ADR 0006：响铃测量的受控协议

- 状态：已采纳
- 日期：2026-10-17

## 背景

"拦截之后还会不会响"是这套方案最容易被误解的一点：即使 `cancelStatus=success`，
用户仍可能听到一声提示音。要做成可断言的事实，必须先解决三个测量障碍：

1. **没有可靠的"响了吗"信号**。`dumpsys audio` 的 focus 日志是有界环形缓冲，
   实测 25 条后停更，不能当计数器；`AudioPlaybackCapture` 拿不到
   `USAGE_NOTIFICATION`（需系统权限）。
2. **托盘状态会改变结果**。同一应用已有通知时，新通知被判为"更新"，系统不打扰。
3. **系统自己有抑制策略**。实测同一应用连发时，第 2 条被打上 flag `2048`
   （合并抑制）或 `32768`（其他抑制），`aboveThreshold=0`。

## 决策

采用 [alert-sound 场景](../../tool/e2e.ps1) 的受控协议，判据取系统 EventLog：

```
notification_alert: [key, user, aboveThreshold, importance, ?, flag]
                    0|pkg|id|tag|uid  1=真的打扰       2048/32768=被系统抑制
```

四条硬约束：

| 约束 | 原因 |
|---|---|
| 每个用例前先 `CLEAR` 清空托盘 | 否则新通知并入已有分组 → 判为更新 → 不打扰 |
| 清空后**静默 ≥8 秒**再发送 | 系统对同一应用的连续通知有抑制窗口；实测 900 ms 时单条用例得到 `alerted=0`，8 s 时稳定 `alerted=1`（4/4） |
| 必须有对照组（放行 + DEFAULT 渠道） | 若对照组不响，说明设备静音/勿扰，全部结论无效；`metrics.ps1 -Gate` 会因此失败 |
| 只断言**单条**用例的响铃 | 多条连发会被系统合并/抑制，"响了几次"不代表"漏了几条" |

## 结果

| 用例 | 入队 | 打扰 | 被拦截 | 结论 |
|---|---|---|---|---|
| 放行 + DEFAULT（对照组） | 1 | 1 | 0 | 仪器有效 |
| 拦截 + DEFAULT | 1 | **1** | 1 | **取消成功也会响** |
| 拦截 + LOW 渠道 | 1 | 0 | 1 | 低重要度天然不响 |
| 拦截 + 3 条间隔 8 s | 3 | 2 | 3 | 仍然响，且系统还会抑制其中 1 条 |
| 拦截 + 5 条连发 | 5 | 1 | 5 | 其余被 2048/32768 抑制 |
| 生成器噪声类别 + 响铃模式 | 3 | 2 | 3 | 真实语料同样漏响 |

## 衍生结论

- 拦截的能力边界应为："能移除通知，**不能阻止首次响铃**"。PLAN §3.5 的措辞据此收敛。
- 要真正静音只有三条路：降渠道重要度（需验证能否改他人渠道）、
  DND 访问权限、厂商白名单。三者都不在本 PoC 范围内。
- 生成器默认把噪声类别放 `IMPORTANCE_LOW`，会让"拦截 = 静音"成为假象；
  因此新增**响铃模式**（`--ez loud true`），用独立高重要度渠道发布噪声类别。
