## 0. 承接第四部分：现有办法剩下的缺口

| 案例 | 现有办法为何不够 |
|---|---|
| P03 被 B 站通知触发 → 看视频 → 翻评论 | 系统只能按**应用**静音。用户想留 B 站，只是不想被这一类推送拉走 |
| P05 微信同时承载工作群与闲聊群 | 系统按应用/联系人控制，做不到**同一应用内按内容区分** |
| P02 清理小红点 | 不看也会被红点拉回去：问题在"通知还在栏里"，不在"响没响" |

缺口一句话：**现有设置能决定"哪个应用能打扰我"，决定不了"什么内容值得打断我"。**

## 1. 价值主张

> 在保持必要信息可达的前提下，按内容规则筛选哪些通知**留在通知栏**。

| 维度 | 内容 |
|---|---|
| 用户任务 | 连续动脑期间，不被打断地完成当前工作 |
| 痛点 | 通知栏里混着必须看的（验证码/银行/工作群）与不值得现在看的（促销/推送） |
| 期望改善 | 必要的留下且可读；不必要的不留在栏里；全部都有记录可查 |

**不承诺**（见第 5 节）：不承诺阻止提示音/振动/横幅，不承诺拦住 ongoing 通知。

## 2. 第一版范围

| 取舍 | 内容 | 依据 |
|---|---|---|
| **核心** | 规则筛选 + 取消：① 白名单放行 ② 关键词/正则/渠道 ③ 兜底拦截 | 451 条应留 0 误拦、452 条应拦 0 漏拦 |

## 3. 技术验证：Android 能做到哪一步

### 3.1 三层分离（本轮最重要的结论）

| 层 | 结论 | 证据 |
|---|---|---|
| **能读到** | ✅ 能，且远不止标题正文 | 全字段入库：title / text / bigText / textLines / subText / category / channelId / groupKey / ongoing / clearable / priority / progress + extras |
| **能移除并留档** | ✅ 能 | 452/452 取消成功（Wilson 下界 99.16%）；历史页可手动查看；重启后仍保留 |
| **能阻止这条通知的提示音** | ❌ **不能** | EventLog 权威判定：对照组 1/1 响（仪器有效），**拦截后仍响 4/5 用例**；`alert→cancel` 只差 4–9 ms |

原文判据：「读到并移除但已经响铃，只支持通知管理可行，不能说防打断成功。」
→ 因此本轮的宣称停在**通知管理（筛选）可行**，不越界到"防打断"。

**关于「首次提醒」这个说法**（作业原文用词）：它指的不是"某个应用只响第一次"，
而是**每一条通知在它发布的那一刻自带的那一次提醒**。

```
第 1 条 post ─► 系统放音(+203ms) ─► 我们收到回调(+208ms) ─► 取消    ← 拦不住那 203ms
第 2 条 post ─► 系统放音(+203ms) ─► 我们收到回调(+208ms) ─► 取消    ← 同样拦不住
第 N 条 post ─► 系统放音(+203ms) ─► 我们收到回调(+208ms) ─► 取消    ← 同样拦不住
```

每走一条通知就重来一遍。第 2 条响不响，取决于系统是否把它合并抑制（实测 3 条间隔 8 s
只响 2 条、5 条连发只响 1 条），与我们无关。

**响铃无法通过优化取消速度解决**（已实测证伪）：ADR 0008 把取消从 466 ms 压到
208 ms 后，6 个响铃用例的结果与优化前**完全一致**。原因在时序而不在速度：

```
post ──────────────────────────► alert（系统放音，+203 ms）
                                    └ 4–9 ms ► cancel（我们取消，+208 ms）
```

系统先播放提示音，再把通知派发给监听器。取消能移除通知栏里的条目，
但不会中断已经播放的声音。唯一的静音路径是把**渠道重要度**降为
`IMPORTANCE_LOW`（需能改他人渠道，普通第三方应用无此权限）或开全局勿扰。

### 3.2 最小验证的观察链（已全部实测）

```
postTime ──► 收到回调 ──► 规则匹配 ──► cancelNotification ──► 通知消失 ──► 落库
   │            │              │                │                │            │
   └─ 系统分发 ─┘  matchedRuleId └─ IPC ~7ms ───┘  onNotificationRemoved └─ 历史 ─┘
        │
        └─► 提示音已在此刻播放，不可撤销（EventLog 的 notification_alert）
```

| 环节 | 观测方式 | 实测 |
|---|---|---|
| 发布 → 回调 | 插桩时间戳 | ~210 ms（模拟器） |
| 匹配 | `matchedRuleId` 落库 | 每条都有 |
| 移除 | `cancelStatus` | 452/452 success |
| 落库 | `history.jsonl` | 903 条，可手动查看 |
| 提示音 | `logcat -b events` 的 `notification_alert` | **已播放，且早于回调** |

### 3.3 时延：哪些可消除

对外口径 = 单条投递、拦截路径。**优化前**（ADR 0008 之前）：

| 路径 | n | 均值 | 95% CI |
|---|---|---|---|
| 单条 · 拦截 | 25 | **466.7 ms** | [465.1, 468.3] |
| 单条 · 保留 | 40 | **212.9 ms** | [211.7, 214.1] |

**差值 253.8 ms**，与代码里写死的 `DEFAULT_DELAY_MS = 250L` 吻合到 4 ms —— 同一套代码、同一引擎，唯一差别是"取消 + 校验"。

| 构成 | 实测 | 占比 | 能消除吗 |
|---|---|---|---|
| 系统分发（post → 回调） | ~210 ms | 45% | ❌ 平台边界 |
| 取消后校验的固定等待 | 250 ms | 54% | ✅ 自设常量，**已改成回调驱动** |
| 判定 + `cancelNotification` IPC | ~7 ms | 1% | ❌ 基本不可压缩 |

已实施优化（ADR 0008）：取消确认由 `onNotificationRemoved` 回调驱动，历史落盘移到独立 IO 线程。

| 指标 | 优化前 | 优化后 | 变化 |
|---|---|---|---|
| 单条 · 拦截 | 466.7 ms（n=25） | **208.6 ms**（n=33，95% CI [207.9, 209.3]） | **-55%** |
| 单条 · 保留 | 212.9 ms（n=40） | 208.8 ms（n=34） | — |
| 批量 800 条均值 | 5219 ms | **319.8 ms** | **-94%** |
| 批量 p95 | 9663 ms | **435 ms** | **-95%** |
| 取消成功率 | 100% | 100%（452/452） | 不变 |
| 判定质量 | 漏 0/451 · 误 0/452 | 漏 0/452 · 误 0/451 | 不变 |

拦截（208.6 ms）与保留（208.8 ms）现在统计上不可区分 → "取消通知"本身几乎不耗时，
剩下的 208 ms 全是系统分发，是平台下限。全量 e2e 复测 PASS 11 / FAIL 0 / OBSERVED 8，无退化。

### 3.4 能力边界（必须主动说）

| 边界 | 证据 |
|---|---|
| ongoing / 进度类通知拦不掉 | API 36 上 `cancelStatus=rejected`，通知仍在 |
| 提示音无法阻止 | 拦截后仍响 4/5 用例；`alert` 只在 `cancel` 前 4–9 ms，属系统时序 |
| 振动、横幅未观测 | 只有声音有 EventLog 证据；振动与横幅无记录，不能宣称已测 |
| 只在模拟器验证 | `sdk_gphone64_x86_64` / Android 16 / API 36 |
| 单一发送方 | 903 条中 884 条来自自建生成器，19 条来自探针；未接微信/B站 |
| 语义局限 | 规则是关键词/正则/渠道，不理解语义；"这条值不值得现在看"仍由用户预设决定 |

## 4. iOS：先核对权限，再决定投入

| 能力 | 苹果有没有 | 我们能用到吗 |
|---|---|---|
| 系统级按应用/联系人过滤 | ✅ 有（Focus） | — |
| 智能选择性提醒 | ✅ 有 | — |
| 通知服务扩展（改本应用通知） | ✅ 有 | ⚠️ 仅限**本应用**发出的通知 |
| 通知过滤 entitlement（需审批） | ✅ 有 | ⚠️ 同上，文档描述的是本应用通知 |
| **读取/拦截其他应用通知** | ❌ 无公开接口 | ❌ 查不到 |

结论：早期实现**先聚焦 Android**，iOS 保留独立交互原型或应用方合作方向，不碰私有 API。

## 5. 能宣称什么 / 不能宣称什么

### 5.1 一句话版

> 第三方 App 可以按内容规则**筛选**其他应用的通知——判定错误率 95% 置信下低于 1%
> （903 条实测），单条 209 ms 内移出通知栏，并留档可查。
> **但不能阻止提示音**：系统在派发回调之前就已播放，实测我们只比它晚 4–9 ms。
> 这是 Android 通知模型的时序约束，不是性能问题。

### 5.2 三段式（缺任一段都会被追问穿）

| 段 | 内容 | 依据 |
|---|---|---|
| **① 能做到** | 读取全字段 → 按规则判定 → 移除并留档 | 452/452 取消成功；漏拦 0/452、误拦 0/451 |
| **② 做不到** | 无法阻止提示音；无法取消 ongoing / 进度类通知 | `alert` 比 `cancel` 早 4–9 ms；`cancelStatus=rejected` |
| **③ 验证范围** | Android 16 模拟器；单一发送方（884/903 条来自自建生成器） | 未接微信、B 站等真实目标；未测振动与横幅 |

### 5.3 可以宣称

| 宣称 | 数字 |
|---|---|
| 能读取其他应用通知的全部字段 | 全字段入库 |
| 能按规则筛选并取消其他应用的通知 | 452/452 成功，Wilson 下界 99.16% |
| 筛选判定错误率低于 1% | 漏拦 0/452、误拦 0/451，双侧 p<0.05 |
| 单条拦截时延 | **208.6 ms**（95% CI [207.9, 209.3]），其中 ~200 ms 是系统分发 |
| 批量 800 条的 p95 | **435 ms** |
| 界面关闭、设备重启后规则仍生效 | e2e `ui-closed` / `reboot-persistence` |
| 时延可拆、可优化 | 466.7 → 208.6 ms（-55%），批量 p95 9663 → 435 ms（-95%） |

### 5.4 不能宣称

| 不能宣称 | 原因 |
|---|---|
| **零漏拦 / 零误拦** | 只能说上界 <1%；要证 <0.5% 需每侧约 600 条，本轮 452/451 |
| "拦截即静音" / "防打断成功" | 4/5 拦截用例仍响；`alert` 只比 `cancel` 早 4–9 ms |
| "能避免首次提醒" | 同问题换词：系统先放音再通知我们，每条通知都这样 |
| "覆盖所有通知类型" | ongoing / progress 被系统拒绝 |
| "已测振动与横幅" | 只有声音有 EventLog 证据，振动/横幅无记录 |
| "跨 ROM 一致" | 只在 Android 16 模拟器验证 |
| "任意第三方 App 已验证" | 884/903 样本来自自建生成器 |
| "无延迟" | 208 ms 是模拟器上的系统分发耗时，真机通常更低但不会归零 |

### 5.5 措辞对照（避免听众误解）

| 不要这样说 | 改成 |
|---|---|
| 无法阻止首次响铃 | **无法阻止这条通知的提示音** |
| 防打断成功 | **通知栏筛选可行** |
| 80% 会响 | **系统决定响不响；只要它响了，我们就来不及** |

## 6. 一句话交接与团队决定

- **商业模式**：一句话 — 面向深度工作的规则筛选，免费基础规则 + 高级规则/统计订阅（假设，未验证）。
- **继续 / 调整**：**继续**，但把承诺从"防打断"收窄为"通知栏筛选"，并把提示音列为已知边界。
- **交接**：技术边界已摸清，下一步是把规则筛选放到真实目标应用上验证。
